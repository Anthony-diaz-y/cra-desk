# CRA Desk — Etapa 3: `sbom` — Plan de implementación

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.
>
> **Modo de trabajo:** el usuario elige cada día entre **tutor** y **avance directo**. En modo tutor, las tareas **[Alumno]** siguen este ciclo: lección corta con un ejemplo de otro dominio, Claude escribe el test, el alumno escribe el código, Claude revisa con pistas progresivas y el alumno anota 3 líneas en `docs/aprendizaje.md`. Las tareas **[Claude]** las hace Claude y luego las explica. En avance directo, Claude implementa todo con TDD.

**Goal:** Cada versión de producto puede tener su SBOM CycloneDX (JSON). La API lo recibe desde la web o la CLI, lo valida, guarda el documento original y extrae sus componentes (nombre, versión, purl), que la Etapa 4 cruzará con OSV y KEV.

**Architecture:** Nuevo módulo `io.cradesk.api.sbom`, que depende de `catalog` (para encontrar la versión dentro de la empresa actual) y de `common`. El parser de CycloneDX es una clase Java pura sobre el árbol de Jackson 3 (`JsonNode`), con tests unitarios rápidos. El documento original se guarda tal cual (texto) junto con su SHA-256, y los componentes en una tabla aparte indexada por purl.

**Tech Stack:** el de las etapas anteriores. Jackson 3 (`tools.jackson`), que ya viene con Spring Boot 4. Sin librerías nuevas.

**Spec:** `docs/superpowers/specs/2026-11-13-cra-desk-design.md` (§2 metas, §5 módulo `sbom` y seguridad "validación de entrada y límite de tamaño de SBOM", §6 etapa 3).

## Global Constraints

- Código, identificadores, mensajes de la API y README en inglés. Explicaciones y `docs/aprendizaje.md` en español.
- **Comentarios:** solo un comentario de una línea en español encima de cada función o método (también tests, constructores y métodos de repositorio), que explica qué hace. Ningún otro comentario: ni Javadoc de clase, ni de campos, ni en línea, ni en SQL, YAML, `pom.xml` o scripts.
- Todos los errores son `ProblemDetail` (RFC 9457) a través de `ApiExceptionHandler` y de las excepciones base de `common`.
- Toda consulta pasa por la empresa actual: a una versión se llega solo a través de un producto encontrado con `CurrentTenant`. Un id de otra empresa da 404.
- Solo se reciben SBOM; CRA Desk no los genera (spec §2, no-metas). Solo CycloneDX JSON; SPDX y VEX quedan fuera (spec §2, no-metas).
- Migraciones nuevas: nunca se edita una migración ya aplicada. Restricciones con nombre explícito. Columnas de texto como `varchar`/`text`, no `char`.
- Maven wrapper fijado en 3.9.16. Tests de integración `*IT.java` y unitarios `*Test.java`, todos con `./mvnw clean verify`.
- Crear repos o hacer push solo con confirmación del usuario.

## Decisiones de diseño de esta etapa (a criterio de quien implementa, spec §7)

| Tema | Decisión | Por qué |
|---|---|---|
| Formato | CycloneDX **JSON** con `bomFormat = "CycloneDX"` y `specVersion` 1.4, 1.5 o 1.6. Otra versión, SPDX o JSON sin `bomFormat` → 400 con el motivo. XML → 415. | Son las versiones que generan hoy Syft, Trivy y cdxgen. Las anteriores a 1.4 no traen todos los campos que usamos. |
| Cómo llega | `PUT /api/products/{id}/versions/{versionId}/sbom` con el JSON como cuerpo crudo (`application/json` o `application/vnd.cyclonedx+json`). | Una sola petición sirve igual para la CLI (`curl --data-binary @bom.json`) y para la web (`fetch` con el archivo). Sin multipart. |
| Un SBOM por versión | Subir otra vez **reemplaza** el anterior en la misma transacción: 201 la primera vez, 200 al reemplazar. | Una versión publicada tiene un solo inventario; reemplazar permite corregir un archivo equivocado. El historial de cambios llegará con la auditoría (Etapa 6). |
| Tamaño | Máximo **5 MB** (`cradesk.sbom.max-bytes`, por defecto 5242880). Se corta leyendo el flujo, no confiando en `Content-Length` → 413 `ProblemDetail`. Máximo **20 000 componentes** → 400. Anidamiento de componentes máximo **16 niveles** → 400. | Un SBOM real de firmware pesa de KB a pocos MB. Los límites evitan agotar la memoria con un archivo enorme o con un JSON muy anidado. |
| Parser | Árbol de Jackson (`JsonNode`) leído a mano en `CycloneDxParser`. Sin validación completa contra el JSON Schema de CycloneDX. | Solo usamos unos pocos campos, el código se entiende entero y no suma dependencias. La validación por esquema queda como mejora futura. |
| Qué se valida | Raíz objeto; `bomFormat` y `specVersion` correctos; `components` (si existe) es un arreglo; cada componente tiene `name` no vacío; un `purl`, si existe, empieza con `pkg:` y tiene tipo y nombre (`pkg:<tipo>/<nombre>`). Los errores se devuelven juntos (hasta 20) en `errors` con la ruta, p. ej. `components[3].name`. | Un purl mal formado rompería el cruce con OSV en la Etapa 4. Ver todos los errores juntos ahorra ida y vuelta. |
| Qué se extrae | De cada componente: `type`, `group`, `name`, `version`, `purl`, `bom-ref`. Los componentes anidados (`components` dentro de un componente) se aplanan. `metadata.component` (el propio producto) **no** se guarda como componente. Se descartan duplicados exactos de (purl, group, name, version). | Es lo que necesita el cruce de vulnerabilidades; el producto no es una dependencia de sí mismo. |
| Componentes sin purl | Se aceptan y se guardan; la respuesta informa `componentsWithoutPurl`. | Muchos SBOM de firmware traen componentes sin purl. Rechazarlos frenaría al usuario; avisarle le permite mejorar su SBOM. |
| Documento original | Se guarda completo en `sboms.document` (`text`), junto con su SHA-256 y su tamaño, y se puede descargar. | El expediente técnico del CRA (Anexo VII) pide conservar el SBOM, y la Etapa 4 podrá volver a leerlo. |
| Quién puede | Subir: `MEMBER` (web) y `CLI` (clave de API). Leer: también `DEMO`. Se registra `uploaded_via` = `WEB` o `CLI`. | Encaja con las reglas de seguridad de la Etapa 2 sin cambiarlas. |
| Concurrencia | La subida bloquea la fila del producto (`findLockedByIdAndOrganizationId`, ya existe en `catalog`). | Dos subidas a la vez de la misma versión quedan una después de la otra, sin estados mezclados. |
| Borrado en cascada | `sbom_components` se borra con su `sboms` (`ON DELETE CASCADE`). `sboms` **no** se borra en cascada con la versión. | Los componentes son datos derivados del documento; la versión es un registro de cumplimiento y ya no se puede borrar. |
| CLI por nombre | La búsqueda de producto y versión por nombre para la CLI (`cradesk upload --product X --version Y`) queda para la Etapa 5. | Se diseña junto con la CLI, cuando se sepa exactamente qué necesita. |

## Review Focus

1. **Archivos enormes o maliciosos:** un cuerpo de 6 MB, un cuerpo enviado por partes sin `Content-Length`, componentes anidados 50 niveles o 25 000 componentes deben dar 413 o 400 `ProblemDetail`, nunca un 500 ni quedarse sin memoria (Tareas 2 y 3).
2. **Lo que no es CycloneDX:** un SPDX JSON, un CycloneDX XML, `specVersion` 1.3, un archivo vacío, `{}` o `[]` deben dar 400 o 415 con un motivo claro (Tareas 2 y 3).
3. **Entre empresas:** subir o leer el SBOM de una versión de otra empresa, o una `versionId` que pertenece a otro producto, debe dar 404 (Tareas 3 y 4).
4. **Reemplazo:** volver a subir deja solo los componentes nuevos, y dos subidas simultáneas a la misma versión terminan con un único SBOM coherente, sin 500 (Tarea 3).
5. **SBOM reales:** componentes sin purl o sin versión, duplicados, anidados, `metadata.component` presente y nombres con Unicode se guardan bien y los conteos cuadran (Tareas 2 y 4).
